## 0. 规则速查

| # | 规则 | 说明 |
| --- | --- | --- |
| 1 | GDScript 函数/变量遵循 `camelCase`；C# 遵循 C# 命名规范 | Godot 引擎回调名称除外 |
| 2 | 不覆盖 Godot 引擎回调的名称或签名 | 如 GDScript `_ready`、C# `_Ready` |
| 3 | 新增公共接口、导出属性和重要成员显式声明类型 | 局部变量可在类型明显时使用推断 |
| 4 | 静态场景属性优先在 Inspector 中配置 | 运行时动态变化的属性由代码控制 |
| 5 | 可复用行为集中在基础脚本/场景或组件中 | 子类和继承场景只实现差异 |
| 6 | 缩进使用 Tab，文件使用 UTF-8、LF，并以一个换行结尾 | 不混用空格缩进 |
| 7 | 节点、资源及信号引用保持可追踪 | 资源移动或改名时同步修复所有引用 |
| 8 | GDScript 与 C# 互操作使用明确、稳定的 API | 注意 Godot 暴露到脚本侧的名称和类型 |

## 1. 通用格式

### 1.1 文件与排版

- 源文件使用 UTF-8 无 BOM、LF 换行，文件末尾保留一个换行。
- GDScript 使用 Tab 缩进；C# 遵循现有文件的格式化风格，不混用 Tab 与空格。
- 代码行尽量控制在 100 个字符以内。较长的条件和调用拆行，保持逻辑结构清楚。
- 一行只写一条语句；不使用压缩成一行的条件分支。
- 运算符两侧留空格，逗号后留空格。字符串优先使用双引号。
- 多行数组、集合、对象初始化按项目所在语言的格式化习惯排版；修改现有代码时沿用邻近代码。

### 1.2 空行与控制流

- 在方法之间以及不相关的逻辑段之间留空行，不用大量空行人为分组。
- 条件、循环和方法体使用标准块结构；避免嵌套过深，优先提前返回。
- 对三元表达式仅用于简单、易读的赋值；复杂分支使用 `if`。
- GDScript 使用 `and`、`or`、`not`，不使用 C 风格布尔运算符。

### 1.3 注释

- 注释符号后留一个空格；代码注释应说明原因、约束或不明显的行为，不复述代码。
- 注释应随实现更新；不要保留与当前代码不符的 TODO、示例或过期路径。
- 玩家可见文字应通过项目已有的本地化方式处理。新增本地化方案前先确认项目当前的翻译资源与调用约定，不要自行引入另一套机制。

## 2. 命名规范

### 2.1 GDScript

| 对象 | 约定 | 示例 |
| --- | --- | --- |
| 函数、变量 | `camelCase` | `takeDamage`、`healthBar` |
| 私有函数、变量 | `camelCase`，不加 `_` 前缀 | `pathIndex`、`collectWeapons` |
| 常量、枚举成员 | `CONSTANT_CASE` | `MAX_HEALTH`、`State.IDLE` |
| `class_name`、内部类、枚举类型 | `PascalCase` | `ATEnemy`、`State` |
| 节点名、Autoload 单例 | `PascalCase` | `StateMachine`、`Game` |
| 信号 | 过去式 + `camelCase` | `enemyDied`、`levelCompleted` |
| GDScript / 场景文件名 | `snake_case` | `enemy_state.gd`、`enemy.tscn` |

> **引擎回调例外**：生命周期回调必须保留 Godot 规定的名称及 `_` 前缀，例如 `_ready`、`_process`、`_physics_process`、`_input` 和 `_draw`。

### 2.2 C#

| 对象 | 约定 | 示例 |
| --- | --- | --- |
| 类型、公共方法、属性、事件 | `PascalCase` | `EasyStarPathfinder`、`FindPath`、`WorkerCount` |
| 参数、局部变量 | `camelCase` | `targetPosition`、`tileSize` |
| 私有字段 | `_camelCase` | `_pathfinder`、`_isReady` |
| 常量 | `PascalCase` | `Walkable`、`MaxRetries` |
| 文件名 | 与主要类型同名 | `EasyStarPathfinder.cs` |

Godot 虚方法使用 API 要求的名称和签名，例如 `_Ready()`、`_Process(double delta)`。不要为了统一普通 C# 命名而改写引擎回调。

### 2.3 跨语言 API

- GDScript 自身声明的函数和变量遵循 `camelCase`；C# 类型、方法和属性遵循 `PascalCase`。GDScript 调用 C# 成员时使用 Godot 实际暴露的 C# API 名称，例如 `_cs.Setup(...)`，不要假设名称会自动转换成 `snake_case`。
- 暴露给 GDScript 的 C# 类型使用 `[GlobalClass]` 时，应保持类型名唯一、稳定，并验证 Godot 能成功构建和加载该类型。
- 对跨语言方法、属性和数据结构，优先使用 Godot 两侧都能可靠传递的公开类型；修改签名时同时检查所有 GDScript、场景和 C# 调用点。
- 不得使用易与 Godot 内置属性、方法或全局函数混淆的成员名。出现 shadowing 警告时应修复命名，而不是忽略警告。

## 3. 类型与错误处理

### 3.1 类型声明

- GDScript 的导出变量、成员变量、函数参数和返回值应显式标注类型；常量也应在类型不明显或接口需要时标注。
- GDScript 局部变量可使用 `:=` 或省略类型，让编译器从明确的右值推断；当推断结果不清晰、为 `Variant` 或会影响接口时，写出具体类型。
- 集合尽量声明元素类型，例如 `Array[ATEnemy]`；确实需要异构数据时才使用未约束的 `Array` / `Dictionary`。
- C# 使用具体类型和 nullable reference types。项目已启用 nullable，可能为空的引用应明确标注并在使用前处理。
- 不要为了消除警告而无依据地添加 `!`、强制转换或默认值；先判断该状态在逻辑上是否允许。

```gdscript
@export var moveSpeed: float = 120.0
var weapons: Array[ATWeapon] = []

func takeDamage(amount: int) -> void:
	health -= amount
```

```csharp
private ATPathfinder? _pathfinder;

public Vector2[] FindPath(Vector2 fromWorld, Vector2 toWorld)
{
    return Array.Empty<Vector2>();
}
```

### 3.2 空值与失败路径

- 对可能不存在的节点使用 `get_node_or_null()` 或 C# 对应的安全查找方式，并在访问前检查结果。
- 使用 `as` 转型或可空类型后，应验证结果再使用；不要把可能的失败伪装成有效对象。
- 对外部输入、资源加载和跨语言边界进行必要校验；失败时返回明确结果或报告有上下文的错误。
- 节点释放、场景切换或 `await` 之后，不假设先前缓存的节点仍有效。
- 不吞掉异常或错误状态。错误恢复、忽略和向上传播应由调用方能理解的契约决定。

## 4. 注释与文档

- GDScript 使用 `##` 编写类、导出属性或公共 API 的编辑器文档；普通实现注释使用 `#`。
- C# 使用 XML 文档注释 `///` 描述被其他模块或 GDScript 使用的公共 API；内部实现只在必要时写普通注释。
- 公共接口文档应说明用途、单位、可空性、边界行为和返回值含义，尤其是空数组、部分结果等特殊约定。
- 代码注释优先使用中文，并使用项目中的现有术语；API 名称、引擎类型名和资源路径保持原样。
- 示例、路径和配置值必须来自当前项目，不能直接复制其他项目的类名、目录或资源约定。

## 5. 脚本组织

### 5.1 GDScript 文件

文件内按以下顺序组织声明和实现；Godot 要求的声明顺序优先：

1. `@tool`、`@icon`、`@static_unload` 等脚本注解。
2. `class_name`、`extends`、类文档注释。
3. `signal`、`enum`、`const`。
4. `@export` 成员。
5. 普通成员变量（公开成员在前；私有成员仍用 `camelCase`，不加 `_`）。
6. `@onready` 节点引用。
7. `_ready()` 及必要的初始化逻辑。
8. 自定义函数，公开接口放在内部辅助函数之前。
9. 其余 Godot 内置虚函数 / 回调放在自定义函数之后，例如 `_process()`、`_physics_process()`、`_input()`、`_unhandled_input()`、`_draw()`、`_notification()`。
10. 内部类。

引擎回调名称和签名不得改写。仅在确有需要时实现对应回调；不要为了补齐顺序而添加空回调。

### 5.2 C# 文件

- 一个主要类型对应一个文件，文件名与类型名一致。
- 使用指令放在命名空间声明外；单一命名空间的文件使用 file-scoped namespace。`using` 按组排列，同组保持稳定顺序。
- 类型内部按以下顺序排列：常量、静态字段、实例字段、构造函数、属性与事件、Godot 生命周期方法、其他公共方法、受保护/显式接口实现、私有辅助方法、嵌套类型。相关成员可在各自区域内按功能相邻排列。
- 字段、属性和方法按可见性组织时，公开 API 在内部实现之前；不要为了字母排序拆散紧密相关的成员。
- 每行一个声明；方法和属性定义之间至少留一空行；使用四个空格缩进及 Allman 大括号风格。
- 微软官方 [.NET C# 编码约定](https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/coding-conventions)规定了上述文件布局和格式原则，但没有规定适用于所有项目的唯一成员顺序；上面的类型成员顺序是本项目统一约定。
- C# 项目设置以 `AwesomeTanks2.csproj` 为准。修改目标框架、nullable 或 Godot SDK 版本前，先确认 Godot .NET 编辑器和构建环境的兼容性。

## 6. 项目结构与架构

### 6.1 目录职责

沿用仓库现有组织方式，将新文件放在最贴近其职责的位置：

| 路径 | 用途 |
| --- | --- |
| `scenes/` | 菜单、关卡、坦克、武器、敌人、特效及 UI 场景 |
| `scripts/` | 按 `autoload/`、`enemies/`、`level/`、`tank/`、`ui/` 等职责划分的脚本 |
| `scripts/pathfinding/` | C# 寻路实现及相关跨语言代码 |
| `data/` | 关卡和其他静态数据 |
| `sprites/`、`sounds/`、`fonts/` | 游戏素材 |
| `shaders/`、`theme/` | 着色器与主题资源 |
| `docs/` | 设计分析、开发计划和项目说明 |
| `tools/` | 编辑器辅助或开发工具，不放运行时核心逻辑 |

GDScript 与场景文件名使用 `snake_case`；脚本成员和节点内的信号连接等符号按对应语言的命名规则处理。全项目迁移时，场景文件改名后须同步更新所有资源路径。避免为单个类新建过深目录，也不要把模块专属实现放到通用目录。

移动、删除或重命名资源时，检查并更新 `preload()` / `load()`、`.tscn` 外部资源路径、`project.godot` Autoload、UID 引用及代码中的字符串路径。保留 Godot 管理的 `.uid` 与导入元数据，不手工伪造 UID。

### 6.2 场景与复用

- 优先复用已有基础场景、脚本和组件。存在多种变体时，考虑通过继承场景或组合共享行为，并让差异集中在数据或小范围覆盖中。
- 可在 Inspector 配置的静态属性（贴图、碰撞层、节点布局、初始数值等）优先留在场景资源中；代码负责运行时状态和行为。
- 不要在 `_ready` 中重复覆盖场景已配置的属性，除非它确实需要根据运行时状态计算。
- 避免用一个大型管理类承载无关系统；模块间通过明确 API 和信号协作。

### 6.3 Autoload、状态与信号

- 全局共享且生命周期确实跨场景的数据或服务才适合注册为 Autoload。注册或改名时同步更新 `project.godot` 及全部引用。
- 避免 Autoload 之间互相持有大量实现细节；对跨模块事件优先使用信号。
- 信号用于通知已经发生的事件，命名应表达事件含义；声明参数类型，并避免在信号里传递不必要的整份节点或全局状态。
- 连接信号时保证连接时机与节点生命周期匹配。重构场景连接时同时检查 `.tscn` 中序列化的连接。
- 静态配置与运行时状态分离。重复出现的游戏数值优先集中管理，避免在多个场景和脚本里复制不同版本。

### 6.4 物理层与分组

物理层使用 `project.godot` `[layer_names]` 中的命名定义，不凭记忆硬编码层号。当前 2D 物理层如下：

| 层 | 名称 |
| --- | --- |
| 1 | `wall` |
| 2 | `player` |
| 3 | `projectile` |
| 4 | `obstacle` |
| 5 | `enemy_spawner` |
| 6 | `enemy` |
| 7 | `fog` |

确需修改层时，检查碰撞层、碰撞遮罩、射线查询及相关场景，避免只更新其中一处。分组名称使用稳定且可读的语义，并集中复用而不是散布拼写变体。

## 7. Godot 与 C# 实践

### 7.1 节点与生命周期

- 节点引用在适当的生命周期阶段获取并缓存；不要在每帧回调中反复按路径查找节点。
- GDScript 的 `$NodePath` / `@onready` 不可用于节点树建立前的初始化阶段；C# 节点查找同样要考虑 `_Ready()` 之前节点尚未就绪的情况。
- `_process` / `_physics_process` 只做需要逐帧执行的工作；不需要时关闭对应处理，或改用信号、计时器和一次性任务。
- 物理移动放在物理处理流程中，并遵循 `CharacterBody2D` 等节点 API 的移动约定。
- 节点通常使用 `queue_free()` 延迟释放；确需立即释放时，确认当前调用栈不会继续使用该对象。

### 7.2 资源与性能

- 固定路径且需要在启动时确定的资源使用 `preload()` 或强类型资源引用；只有路径在运行时确定时才动态加载。
- 频繁使用的资源或场景应缓存，避免在高频回调中重复加载、创建临时集合或拼接大量字符串。
- 使用 `Timer`、Tween、AnimationPlayer 或信号表达等待与动画，不用持续轮询替代已有机制。
- 性能优化应针对可观察的热点，优先保持行为正确和代码清晰。

### 7.3 GDScript 与 C# 互操作

- 对 C# 侧的公开类型、方法或属性做改动时，检索 GDScript 的调用点，并验证导出到 Godot 后的名称和类型。
- 对 GDScript 可见的 C# Godot 对象遵守 Godot 对 partial 类型、导出成员和引擎生命周期方法的要求。
- 避免把 C# 专有类型直接暴露给 GDScript；优先使用 Godot 支持的基础类型、Godot 数学类型及可互操作的数组/资源类型。
- 修改返回值、参数、数组形态或 null 行为时，明确处理两侧的转换与失败情况，并至少完成一次 Godot .NET 构建或编辑器加载验证。
- C# 的线程工作不得直接从后台线程操作场景树或 UI；需要更新场景时切回 Godot 主线程。

### 7.4 调试与验证

- 修复问题时，先定位具体行为由哪个脚本、场景或资源控制；尽量在所属模块内修复根因。
- 新增逻辑时验证正常路径及关键边界，例如无目标、无节点、空资源、实体释放和场景切换。
- 运行项目已有且与修改相关的检查；若没有自动化测试，至少通过 Godot 编辑器解析/构建，并在可行时验证对应场景行为。
- 不忽略新增的解析错误、构建错误和相关警告。无关的既有问题应单独记录，不扩大本次修改范围。

## 8. 提交前检查

- [ ] GDScript 函数/变量使用 `camelCase`，私有成员不加 `_`，信号使用过去式 `camelCase`；常量为 `CONSTANT_CASE`，类/枚举/节点/Autoload 为 `PascalCase`，文件名为 `snake_case`。
- [ ] C# 命名符合 .NET 约定；Godot 回调保留要求的名称与签名，GDScript 调用 C# API 时使用其实际暴露名称。
- [ ] 公共接口、导出属性和跨语言边界类型明确；空值和失败路径有处理。
- [ ] 未新增与 Godot 内置成员冲突的名称，也未忽略新增警告。
- [ ] 场景 Inspector 中已有的静态配置没有被代码无故覆盖。
- [ ] 复用已有场景、脚本、数据和信号约定，没有复制另一份相同逻辑。
- [ ] 物理层使用 `project.godot` 的命名定义；层或遮罩变更已检查所有关联资源。
- [ ] 资源路径、Autoload、场景信号连接及 UID 引用在资源移动后仍有效。
- [ ] 高频回调没有重复查找节点、加载资源或进行不必要的分配。
- [ ] 注释和文档描述当前行为，玩家可见文字遵守项目本地化方式。
- [ ] 已运行与改动相关的解析、构建或场景验证，并处理本次引入的问题。
